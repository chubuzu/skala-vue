# 데이터 연결 상세 — 어떤 값이 어디서 나와 어디로 가는가

`개념-점검표.md`가 "어떤 문법이 어디 있나"라면, 이 문서는 **"어떤 값이 어떤 경로로 화면까지 도달하나"**를
필드 단위로 추적한 것입니다. 줄 번호는 실제 코드 기준입니다.

---

## 1. 검색어 — 4방향 순환 구조

이 앱에서 가장 많은 방향으로 연결된 값입니다. **`searchQuery` 하나가 4곳과 양방향으로 묶여 있습니다.**

```
                    ┌──────────────────────────┐
                    │  HomeView.searchQuery    │  ← 단일 진실 공급원 (ref)
                    └──────────────────────────┘
        ①↑ ②↓                              ③↓        ④↕
   ┌─────────┐                    ┌──────────────┐  ┌──────────┐
   │SearchBox│                    │filteredWeather│  │주소창 URL│
   │ (input) │                    │  List (계산)  │  │ ?search= │
   └─────────┘                    └──────────────┘  └──────────┘
                                          ↓
                                    WeatherList
                                          ↓
                                    WeatherCard
```

### ① 사용자 타이핑 → 상태

| 단계 | 위치 | 코드 |
|---|---|---|
| 1 | `SearchBox.vue:23` | `<input v-model="inner">` — 네이티브 input이 `inner`를 씀 |
| 2 | `SearchBox.vue:14` | `inner`의 **setter**가 발동 → `emit('update:modelValue', value)` |
| 3 | `HomeView.vue:241` | `<SearchBox v-model="searchQuery" />`가 그 이벤트를 받아 `searchQuery` 갱신 |

`inner`는 실제 값을 저장하지 않습니다. **읽기는 `props.modelValue`, 쓰기는 `emit`으로 흘려보내는 통로**입니다.

```js
// SearchBox.vue:12-15
const inner = computed({
  get: () => props.modelValue,              // 부모 값을 그대로 읽음
  set: (value) => emit('update:modelValue', value)  // 저장하지 않고 부모에게 넘김
})
```

### ② 상태 → 입력창 되돌아오기

`searchQuery`가 바뀌면 → `:modelValue` prop → `inner`의 getter → `<input>`의 value.
④에서 URL이 바뀌어 `searchQuery`가 변할 때 **입력창이 자동으로 따라오는 이유**가 이 경로입니다.

### ③ 상태 → 필터링된 목록 → 카드

```js
// HomeView.vue:168-186
const filteredWeatherList = computed(() => {
  const keyword = searchQuery.value.trim()

  const matched = keyword
    ? weatherList.value.filter(
        (city) =>
          city.name.includes(keyword) ||    // 구장명
          city.teams.includes(keyword) ||   // 구단명
          city.region.includes(keyword)     // 지역명
      )
    : weatherList.value

  return [...matched].sort((a, b) => sortRank(a) - sortRank(b))
})
```

**검색 대상 필드 3개**는 `stadiums.js`의 `name`, `teams`, `region`입니다.
따라서 "잠실", "두산", "서울" 모두 같은 카드를 찾아냅니다.

여기서 **`favoriteStore`도 함께 읽습니다**(`sortRank` 내부, 155행).
그래서 즐겨찾기 별표를 누르면 **검색어를 건드리지 않았는데도 목록 순서가 즉시 바뀝니다.**
computed가 두 개의 반응형 소스에 동시에 의존하는 사례입니다.

이후 `HomeView.vue:246` → `WeatherList :weatherList` → `pagedList`(5개씩 잘라냄) → `WeatherCard :city`

### ④ 상태 ↔ 주소창 (양방향)

```js
// 정방향 — HomeView.vue:198
watch(searchQuery, (keyword) => {
  if (keyword === readSearchFromUrl()) return    // ← 루프 차단기
  router.replace({ query: keyword ? { ...route.query, search: keyword } : /* search 키 제거 */ })
})

// 역방향 — HomeView.vue:211
watch(() => route.query.search, () => {
  const fromUrl = readSearchFromUrl()
  if (fromUrl !== searchQuery.value) searchQuery.value = fromUrl   // ← 루프 차단기
})
```

**두 watch가 서로를 트리거하지만 무한 루프가 안 나는 이유**: 양쪽 첫 줄에서 값이 같으면 즉시 `return`합니다.
정방향이 URL을 바꾸면 역방향이 깨어나지만, 그때 값이 이미 같으므로 거기서 멈춥니다.

`readSearchFromUrl()`(38행)이 `typeof raw === 'string'`을 검사하는 이유는
`?search=a&search=b`처럼 들어오면 vue-router가 **배열**을 주기 때문입니다.

## 2. 날씨 — API 응답 필드가 화면 픽셀이 되기까지

### OpenWeatherMap `/weather` 응답 → 앱 내부 형태

`weatherApi.js:24-42`에서 중첩된 원본을 평평하게 폅니다.

| 원본 JSON 경로 | 변환 | 앱 필드 | 최종 도착지 |
|---|---|---|---|
| `data.main.temp` | `Math.round()` | `temp` | `displayTemp` → `{{ }}`, 직관 지수 입력 |
| `data.weather[0].description` | 그대로 | `status` | 카드 하단 텍스트, `weatherEmoji()` 입력 |
| `data.weather[0].icon` | 그대로 | `icon` | `weatherEmoji()` 입력 |
| `data.main.humidity` | 그대로 | `humidity` | 상세 텍스트, 직관 지수 입력 |
| `data.wind.speed` | `?? null` | `windSpeed` | 직관 지수 입력, `WindIndicator :speed` |
| `data.wind.deg` | `?? null` | `windDeg` | `WindIndicator :wind-deg` |
| `data.sys.sunset` | `?? null` | `sunset` | `ShadeTimeline :sunset` |

`?? null`로 통일하는 게 중요합니다. `undefined`가 섞이면
`comfortScore()`의 `== null` 검사가 일관되게 동작하지 않습니다.

### 기온 하나가 화면에 찍히기까지

```
data.main.temp  (28.37)
    ↓ weatherApi.js:25   Math.round
temp  (28)                                    ← 항상 섭씨로 보관
    ↓ StadiumDetailView.vue:59
displayTemp = convertTemp(weather.temp, configStore.unit)
    ↓ temperature.js:3   화씨면 ×9/5+32
    ↓ StadiumDetailView.vue:195
{{ displayTemp }}{{ configStore.unitSymbol }}   →  "28℃" 또는 "83℉"
```

**원본은 항상 섭씨로 보관하고 표시 직전에만 변환합니다.**
그래서 `UnitToggler`를 눌러 `configStore.unit`만 바꾸면
`convertTemp`를 쓰는 **모든 화면이 동시에 바뀝니다.** 재조회는 없습니다.

### `/forecast` 응답의 두 갈래 가공

같은 엔드포인트를 부르지만 **가공 방식이 달라 용도가 갈립니다.**

```
                        data.list (3시간 간격 40개)
                       ╱                          ╲
     fetchForecast (weatherApi.js:46)      fetchDailySummary (weatherApi.js:120)
              slice(0, 8)                     날짜별로 접기
                  ↓                                 ↓
     [{time, temp, status, icon,          { '2026-08-15': {
       precipitationChance,                   icon, status, maxTemp, minTemp,
       humidity, windSpeed}, ...]             precipitationChance,
                  ↓                            evening: {temp, humidity,
     시간별 예보 스트립                                    windSpeed,
     (StadiumDetailView.vue:225)                          precipitationChance}
                                                } }
                                                    ↓
                                          날짜 칩 + 직관 지수 입력
```

`evening`이 이 프로젝트의 핵심입니다. `weatherApi.js:158-171`에서 만들어집니다.

```js
const gap = Math.abs(hour - GAME_HOUR)          // GAME_HOUR = 18
if (eveningGap[date] === undefined || gap <= eveningGap[date]) {
  eveningGap[date] = gap
  byDate[date].evening = { temp, humidity, windSpeed, precipitationChance }
}
```

`<=`(미만이 아니라 이하)인 이유: 15시와 21시가 똑같이 3시간 차이로 비길 때
**나중에 순회하는 21시가 이깁니다.** 경기 후반 관람 환경에 더 가깝기 때문입니다.

### `pop` 필드의 단위 변환

`data.list[].pop`은 0~1 실수입니다. `weatherApi.js:69`에서 `Math.round(pop * 100)`으로 %로 바꿔
`precipitationChance`라는 이름으로 내보냅니다. 이후 모든 코드는 0~100 정수로 다룹니다.

"화면마다 점수가 달랐다"는 과거 버그가 여기서 나왔습니다.

```

        ┌─────────────┬───────┴────────┬──────────────┐

```

| 필드 | 사용 함수 | 위치 |
|---|---|---|
| `temp` | `tempPenalty` + 다른 3개의 조건 | `comfortScore.js:17` |

이 파일이 앱 전체의 기준 데이터입니다. **필드마다 소비처가 완전히 다릅니다.**

| | `StadiumsView:20` | "돔" 태그 |

### `cfBearing`이 두 계산에 쓰이는 방식

같은 값을 쓰지만 **비교 대상이 다릅니다.**

```
바람 (WindIndicator)                     그늘 (ShadeTimeline)
  weather.windDeg                          getSunPosition() → azimuth
      ↓ +180° (불어오는 → 불어가는)              ↓
  analyzeWind(blowingTo, cfBearing)        toFieldRelativeAngle(azimuth, cfBearing)
      ↓                                        ↓
  angleToZone() → 외야/1루/홈뒤/3루         angleToZone() → 같은 4구역
      ↓                                        ↓
  "외야 방향 (뜬공 비거리 ↑)"                "3루 측 그늘"
```

`fieldDirection.js`의 `toFieldRelativeAngle`과 `angleToZone`을 **두 컴포넌트가 공유**합니다.
`WindIndicator`는 `analyzeWind`로 감싸 쓰고, `ShadeTimeline`은 두 함수를 직접 씁니다.

풍향에 `+180°`를 더하는 이유(`fieldDirection.js:47`): 기상 관측의 풍향은 **바람이 불어오는 쪽**이라,
"어디로 부는가"로 뒤집어야 타구 영향을 말할 수 있습니다.

```js
const SCHEDULE = localScheduleModule?.default ?? null
```

일반 `import`면 파일이 없을 때 **빌드가 실패**합니다. `import.meta.glob`은 매칭이 없으면 빈 객체를 주므로
클론 직후에도 앱이 뜹니다. 이후 모든 함수가 `if (!SCHEDULE) return []`로 방어합니다.

### 범위 밖 처리가 두 단계인 이유

```js
// kboScheduleApi.js:70
if (!isWithinScheduleRange(dateStr)) {
  resolve({ outOfRange: true, games: [] })   // "일정을 모른다"
}
```

이건 **일정 데이터 범위**(2026-08-01 ~ 09-06)이고, 직관 지수의 "예보 범위 밖"은
**OpenWeatherMap 5일 제한**입니다. 원인이 달라 메시지도 다릅니다.

**5개 진입점이 하나의 진행 바로 모입니다.**

`holding`은 별개입니다. 청크가 캐시돼 0ms에 끝나면 바가 안 보이므로,
최소 400ms를 채우려고 붙잡아 두는 상태입니다 (`uiStore.js:81-89`).

## 7. 라우트 파라미터 — URL 한 조각이 화면 전체를 결정

```
/stadium/stadium_01
        ↓ route.params.stadiumId
StadiumDetailView.vue:25  findStadiumById() → stadium (computed)
        ↓
  ├─ stadium.lat/lon      → fetchCurrentWeather / fetchForecast / fetchDailySummary
  ├─ stadium.id           → getStadiumGameDates() → gameDates → DateSelector
  ├─ stadium.id           → favoriteStore.isFavorite()
  ├─ stadium.cfBearing    → WindIndicator, ShadeTimeline
  ├─ stadium.isDome       → 바람·그늘 카드 표시 여부, 직관 지수 100점
  └─ stadium.mockTemp     → API 실패 시 폴백
```

**같은 컴포넌트가 재사용될 때의 함정**과 그 해결:

```js
// StadiumDetailView.vue:161-162
onMounted(loadAll)
watch(() => route.params.stadiumId, loadAll)   // ← 이게 없으면 데이터가 안 바뀜
```

`/stadium/stadium_01`에서 `/stadium/stadium_02`로 이동하면 vue-router는 **컴포넌트를 재사용**합니다.
`onMounted`가 다시 돌지 않으므로 `watch`로 세그먼트 변화를 직접 잡아야 합니다.

`stadium`은 computed라 자동으로 갱신되지만, **API 호출은 부수효과라 자동으로 안 됩니다.**
이 구분이 핵심입니다.

## 8. 컴포넌트 3단 이벤트 중계

**아래에서 위로 올라가는 유일한 경로**입니다.
