# 관계별 개념 정리 — 어느 파일과 어느 파일 사이에 무엇이 있는가

같은 12개 점검 항목을 **개념 순서가 아니라 파일 사이의 관계 순서**로 다시 정리했습니다.
"이 두 파일은 어떻게 연결돼 있고, 그 연결에서 어떤 문법이 쓰였는가"를 기준으로 읽습니다.

---

## 관계 지도

```
                          main.js
                             │ use(Pinia) → use(Router) → use(ElementPlus)
                          App.vue
        ┌───────────────┬─────┴──────┬────────────────┐
   GlobalProgressBar  NavBar   ApiKeyNotice      RouterView
        │               │             │               │
     [uiStore]     UnitToggler    [weatherApi]   router/index.js
                        │                              │  ← Navigation Guard
                   [configStore]                       │
        ┌───────────────┬──────────────┬───────────────┴──┬─────────────┐
    HomeView    StadiumDetailView   ScheduleView      PlanView    StadiumsView
        │               │                │                │            │
   SearchBox       DateSelector ────────┘                 │        el-table
   WeatherList     WindIndicator                          │
        │          ShadeTimeline                          │
   WeatherCard     TempBadge                              │
        │          StadiumImage                           │
   ComfortBadge ◄──────┴──────── AddToPlanButton ◄────────┘

        │

`[대괄호]`는 Pinia 스토어입니다. **부모-자식 관계 없이도 연결되는 통로**입니다.

## 관계 ① App.vue ↔ NavBar · GlobalProgressBar · ApiKeyNotice

**props가 하나도 없는 관계입니다.** 세 자식 모두 부모에게서 값을 받지 않고 각자 알아서 구합니다.

```html
<!-- App.vue:10-17 -->
<GlobalProgressBar />          <!-- props 없음 -->
<div id="app">
  <NavBar />                   <!-- props 없음 -->
  <ApiKeyNotice />             <!-- props 없음 -->
  <RouterView />
</div>
```

| 자식 | 값을 어디서 구하나 |
|---|---|
| `GlobalProgressBar` | `useUiStore()` — 스토어 직결 |
| `NavBar` | `usePlannerStore()` + `RouterLink` |
| `ApiKeyNotice` | `hasApiKey()` — API 모듈 직접 import |

> **설명 포인트**: "전역에 걸친 관심사는 props로 내려보내지 않고 자식이 직접 가져온다."
> `ApiKeyNotice`는 원래 `HomeView` 안에 있었는데, 주소창에 `/stadium/xxx`를 직접 입력하면
> 경고 없이 목데이터가 실제 날씨처럼 보이는 문제가 있어 `App.vue`로 올렸습니다. (`ApiKeyNotice.vue:2-4` 주석)

`GlobalProgressBar`는 `<Transition>`으로 감싸 페이드 처리했고,
`@media (prefers-reduced-motion: reduce)`로 애니메이션 민감 사용자를 배려했습니다.

**여기서 확인되는 항목**: Element Plus(`el-alert`), 컴포넌트 등록 방식(전역 등록 0개, 전부 지역 import)

## 관계 ② NavBar ↔ UnitToggler — 형제가 스토어로 대화

```
UnitToggler.vue:7   configStore.toggleUnit()      ← 쓰기
        ↓ (Pinia)
WeatherCard.vue:21 / StadiumDetailView.vue:59 / PlanView.vue:155   ← 읽기
```

`UnitToggler`는 `NavBar` 안에 있지만, 그 결과는 **완전히 다른 화면의 컴포넌트들에 도달**합니다.
props/emit으로는 불가능한 연결이고, 이게 Pinia를 쓰는 이유입니다.

```js
// configStore.js
const unit = ref('celsius')                                        // state
const unitSymbol = computed(() => unit.value === 'celsius' ? '℃' : '℉')  // getter
function toggleUnit() { unit.value = unit.value === 'celsius' ? 'fahrenheit' : 'celsius' }  // action
```

`UnitToggler.vue:15,22`는 `:class="{ active: configStore.unit === 'celsius' }"`로
현재 단위를 시각적으로 표시합니다 — **v-bind 객체 문법**.

> **중요**: 기온 원본은 항상 섭씨로 보관하고 `convertTemp()`로 표시 직전에만 바꿉니다.
> 그래서 토글해도 **API 재호출이 없습니다.**

**여기서 확인되는 항목**: Pinia(state/getter/action 3종), v-bind

## 관계 ③ HomeView ↔ SearchBox — v-model을 직접 구현

**이 관계 하나에 props·emits·computed·v-model·slot이 전부 들어 있습니다.**

```
HomeView.vue:241   <SearchBox v-model="searchQuery" />
                            ↓ 펼치면
                   :modelValue="searchQuery"
                   @update:modelValue="searchQuery = $event"
```

```js
// SearchBox.vue:5-15
const props = defineProps({ modelValue: { type: String, default: '' } })
const emit = defineEmits(['update:modelValue'])

const inner = computed({
  get: () => props.modelValue,                       // 부모 값을 읽기만
  set: (value) => emit('update:modelValue', value)   // 저장하지 않고 부모에게 넘김
})
```

```html
<!-- SearchBox.vue:20-27 -->
<BaseDashboardCard title="구단 · 구장 검색">     <!-- Slot 소비 -->
  <div class="search-field">
    <input v-model="inner">                      <!-- v-model (네이티브) -->
    <button v-if="modelValue" @click="inner = ''">✕</button>
  </div>
</BaseDashboardCard>
```

**핵심**: `inner`는 값을 저장하지 않습니다. 읽기는 props, 쓰기는 emit으로 흘려보내는 **통로**입니다.
`@click="inner = ''"`로 setter를 발동시켜 부모 값을 지우는 것도 같은 원리입니다.

> `v-model`이 `:modelValue` + `@update:modelValue`의 문법 설탕이라는 걸
> 이 파일 하나로 증명할 수 있습니다.

**여기서 확인되는 항목**: v-model(커스텀+네이티브), props, emits, computed(getter/setter), Slot 소비, v-if

## 관계 ④ HomeView → WeatherList → WeatherCard → ComfortBadge — 3단 하강·3단 상승

이 프로젝트에서 **가장 깊은 컴포넌트 체인**입니다. 데이터는 내려가고 이벤트는 올라옵니다.

### 내려가는 길 (props)

```
HomeView.vue:246
  <WeatherList :weather-list="filteredWeatherList" :today-game-map="todayGameMap" ... />
        ↓ WeatherList.vue:20  pagedList (5개씩 자름)
  <WeatherCard :city="city" :today-game="todayGameMap[city.id] ?? null" />
        ↓ WeatherCard.vue:54
  <ComfortBadge :weather="city.scoreWeather ?? city" :is-dome="..." :basis="city.scoreBasis" />
```

### 올라오는 길 (emit)

```
WeatherCard.vue:59   @click.stop="emit('detail', city)"
        ↑
WeatherList.vue:52   @detail="emit('detail', $event)"     ← 자기 일이 아닌 걸 그대로 중계
        ↑
HomeView.vue:250     @detail="showDetail"
        ↓
HomeView.vue:229     router.push(`/stadium/${city.id}`)
```

**`WeatherList`가 중간에서 하는 일**이 설명 포인트입니다.
자기가 처리할 이벤트가 아닌데 `$event`를 그대로 위로 넘깁니다. 중간 컴포넌트가
데이터를 가공하지 않고 통과시키는 패턴입니다.

### 이벤트 수식어가 필요한 이유가 여기서 나옵니다

```html
<!-- WeatherCard.vue:28 — 카드 전체가 클릭 대상 -->
<div class="card" @click="emit('select', city)">
  <!-- :31 — 별표를 누르면 카드 클릭이 같이 발동하면 안 됨 -->
  <button @click.stop="favoriteStore.toggleFavorite(city.id)">
  <!-- :59 — 상세보기도 마찬가지 -->
  <button @click.stop="emit('detail', city)">
```

부모가 클릭 핸들러를 갖고 있는데 자식 버튼이 따로 있어서, **버블링을 끊지 않으면 두 동작이 동시에** 일어납니다.

### WeatherCard가 스토어를 직접 쓰는 부분

```js
// WeatherCard.vue:18-22
const configStore = useConfigStore()
const favoriteStore = useFavoriteStore()
const displayTemp = computed(() => convertTemp(props.city.temp, configStore.unit))
const isFavorite = computed(() => favoriteStore.isFavorite(props.city.id))
```

**props와 스토어를 섞어 씁니다.** 구장 데이터는 부모에게서(props), 단위·즐겨찾기는 스토어에서.
"이 컴포넌트만의 값"과 "앱 전체가 공유하는 값"을 구분한 결과입니다.

> **연쇄 효과**: `WeatherCard`에서 별표를 누르면 → `favoriteStore` 변경 →
> `HomeView.vue:168`의 `filteredWeatherList`가 `sortRank`(155행)를 통해 스토어를 읽고 있어서
> → **목록 순서가 즉시 재정렬됩니다.** 검색어를 건드리지 않았는데도요.

**여기서 확인되는 항목**: props(3단), emits(중계), 이벤트 수식어(`.stop`), computed, Pinia, v-for·:key, Programmatic Navigation

## 관계 ⑤ WeatherList ↔ PagerDots — 커스텀 이벤트 + Named Slot

```html
<!-- WeatherList.vue:57-63 -->
<template v-if="totalPages > 1" #footer>        <!-- 부모(BaseDashboardCard)의 footer 슬롯에 주입 -->
  <PagerDots
    :current-page="currentPage"
    :total-pages="totalPages"
    @change="currentPage = $event"              <!-- update:modelValue가 아닌 커스텀 이름 -->
  />
</template>
```

`SearchBox`·`DateSelector`는 `update:modelValue`(v-model 규약)를 쓰는데
`PagerDots`는 `change`라는 **커스텀 이벤트명**을 씁니다. 두 방식을 비교해 보여주기 좋습니다.

`WeatherList`는 **자기가 슬롯을 소비하면서 동시에 자식을 그 슬롯에 넣습니다.**
`BaseDashboardCard`의 `#actions`에는 결과 개수를, `#footer`에는 페이지네이션을 넣습니다.

```js
// WeatherList.vue:26-31 — 검색으로 목록이 바뀌면 1페이지로 리셋
watch(() => props.weatherList, () => { currentPage.value = 1 })
```

**props를 watch하는 사례**입니다. 게터 함수 문법(`() => props.x`)을 써야 하는 이유는
`props.weatherList`를 그대로 넘기면 값이 아니라 스냅샷이 전달되기 때문입니다.

**여기서 확인되는 항목**: props, 커스텀 emit, Named Slot(주입), watch(props 감시)

## 관계 ⑥ 5개 화면 ↔ BaseDashboardCard — Named Slot 집합소

**슬롯 4종이 한 컴포넌트에 다 들어 있습니다.**

```html
<!-- BaseDashboardCard.vue:12-36 -->
<section class="dashboard-card" :class="{ flush }">
  <header v-if="title || $slots.header || $slots.actions">
    <slot name="header">
      <h2 class="card-title">{{ title }}</h2>      <!-- ① fallback 있는 named slot -->
    </slot>
    <div v-if="$slots.actions">
      <slot name="actions" />                       <!-- ② 조건부 렌더 -->
    </div>
  </header>

  <div class="card-body">
    <slot>
      <p class="placeholder">표시할 내용이 없습니다.</p>   <!-- ③ default + fallback -->
    </slot>
  </div>

  <footer v-if="$slots.footer">
    <slot name="footer" />                          <!-- ④ -->
  </footer>
</section>
```

| 기법 | 의미 |
|---|---|
| `<slot name="header">기본값</slot>` | 부모가 안 넣으면 `title` prop이 제목이 됨 |
| `v-if="$slots.actions"` | **넘어온 내용이 있을 때만** 감싸는 div를 그림 (빈 여백 방지) |
| `:class="{ flush }"` | Boolean prop으로 본문 여백 제거 (표처럼 가장자리까지 채울 때) |

### 사용처별 슬롯 조합

| 사용처 | 쓰는 슬롯 |
|---|---|
| `SearchBox.vue:20` | default만 |
| `WeatherList.vue:36` | default + `#actions`(개수) + `#footer`(페이지네이션) |
| `StadiumDetailView` (4회) | 각각 default |
| `PlanView.vue:131` | default + `#actions`(전체 비우기 버튼) |

> **핵심**: 부모 5개가 같은 껍데기를 쓰면서 내용물만 다릅니다.
> 카드 디자인(배경·라운드·그림자·여백)을 한곳에서 관리할 수 있습니다.

**여기서 확인되는 항목**: Slot(named 3종 + default), fallback, `$slots` 검사, Boolean props

## 관계 ⑦ StadiumDetailView · ScheduleView ↔ DateSelector — 한 자식, 두 부모

**같은 컴포넌트를 두 화면이 공유하는데 넘기는 props가 다릅니다.**

```html
<!-- StadiumDetailView.vue:266 — 날씨 요약을 함께 넘김 -->
<DateSelector v-model="selectedDate" :dates="gameDates" :daily-weather="dailyWeather" />

<!-- ScheduleView.vue:94 — 날짜만 -->
<DateSelector v-model="selectedDate" :dates="scheduleDates" class="date-strip" />
```

`dailyWeather`가 선택 사항이라 기본값을 **팩토리 함수**로 줍니다.

```js
// DateSelector.vue:9
dailyWeather: { type: Object, default: () => ({}) }   // 객체 기본값은 반드시 함수로

없으면 칩에 날씨 아이콘 대신 `·`가 표시됩니다(`DateSelector.vue:47`).

watch(selectedDate, (newDate) => { /* 경기만 다시 */ })

## 관계 ⑧ 3개 화면 ↔ AddToPlanButton — 자식이 스토어에 직접 쓴다

**부모가 셋인데 emit이 하나도 없습니다.** 자식이 스토어를 직접 씁니다.

```js
// AddToPlanButton.vue:12-18
const plannerStore = usePlannerStore()
const planned = computed(() => plannerStore.isPlanned(props.game.date, props.game.stadiumId))
function toggle() { plannerStore.togglePlan(props.game) }
```

```html
<!-- AddToPlanButton.vue:22-27 -->
<!-- .stop: 목록 행이 RouterLink인 경우 담기 버튼 클릭으로 페이지가 이동하지 않도록 -->
<button :class="[variant, { on: planned }]" @click.stop.prevent="toggle">
```

**수식어 체이닝(`.stop.prevent`)이 필요한 유일한 곳**입니다.
`ScheduleView`에서 경기 행 전체가 `<RouterLink>`라, `.stop`으로 버블링을 막고
`.prevent`로 링크 기본 동작까지 막아야 합니다.

### 부모 3곳이 `game` 객체를 조립해 넘깁니다

```html
<!-- ScheduleView.vue:125 / StadiumDetailView.vue:281 — 같은 모양을 각자 만듦 -->
:game="{ date, stadiumId, homeTeam, awayTeam, startTime }"

<!-- PlanView.vue:161 — row가 이미 같은 필드를 가짐 -->
:game="row"
```

### 결과가 도달하는 곳

```
AddToPlanButton.vue:17  togglePlan()
        ↓ [plannerStore]
  NavBar.vue:17         planCount → 네비게이션 배지 숫자
  PlanView.vue:30       sortedPlans → 목록
  PlanView.vue:102      watch(plans.length) → 날씨 재조회
```

**경기 일정에서 버튼을 누르면 네비게이션 바 숫자가 즉시 올라갑니다.**
두 컴포넌트는 서로를 모르고 스토어만 공유합니다.

**여기서 확인되는 항목**: 이벤트 수식어 체이닝, props, Pinia(인자 받는 getter), computed, v-bind 배열+객체 혼합

## 관계 ⑨ StadiumDetailView ↔ WindIndicator · ShadeTimeline — props → 순수 함수

**컴포넌트가 계산을 직접 하지 않고 `utils/`에 위임합니다.**

```html
<!-- StadiumDetailView.vue:239-243 -->
<WindIndicator
  v-if="weather.windDeg != null"          <!-- 데이터 없으면 아예 안 그림 -->
  :wind-deg="weather.windDeg"             <!-- API에서 온 값 -->
  :speed="weather.windSpeed ?? 0"
  :cf-bearing="stadium.cfBearing"         <!-- 마스터 데이터에서 온 값 -->
/>

<!-- :250 -->
<ShadeTimeline :stadium="stadium" :date="selectedDate || todayString" :sunset="weather.sunset" />
```

**출처가 다른 두 데이터를 한 컴포넌트에서 합칩니다** — API 응답(`windDeg`)과 정적 데이터(`cfBearing`).

```js
// WindIndicator.vue:11    → utils/fieldDirection.js
const analysis = computed(() => analyzeWind(props.windDeg, props.cfBearing))

// ShadeTimeline.vue:16-33 → utils/sunPosition.js + fieldDirection.js
const { altitude, azimuth } = getSunPosition(localDate, props.stadium.lat, props.stadium.lon)
const relative = toFieldRelativeAngle(azimuth, props.stadium.cfBearing)
```

두 컴포넌트가 **`fieldDirection.js`를 공유**하되 비교 대상만 다릅니다 — 풍향 vs 태양 방위각.

돔구장이면 부모가 **카드 자체를 안 그립니다**.

```html
<!-- StadiumDetailView.vue:236, 250 -->
<BaseDashboardCard v-if="!stadium.isDome" title="바람 · 타구 영향">
<BaseDashboardCard v-if="!stadium.isDome" title="시간대별 그늘 예상">
<BaseDashboardCard v-else title="돔구장">
```

**여기서 확인되는 항목**: props(required), computed, v-if/v-else, v-bind(동적 `:transform`), SVG

## 관계 ⑩ StadiumsView ↔ Element Plus — Scoped Slot을 **소비**하는 곳

**el-table이 넘겨주는 `row`를 받는 유일한 사례입니다.**

```html
<!-- StadiumsView.vue:15-31 -->
<el-table :data="stadiums">
  <el-table-column prop="teams" label="구단" min-width="170" />

  <el-table-column label="홈구장" min-width="160">
    <!-- Scoped Slot: el-table이 넘겨주는 row로 구장명을 강조 표시 -->
    <template #default="{ row }">
      <span class="stadium-name">{{ row.name }}</span>
      <span v-if="row.isDome" class="dome-tag">돔</span>
    </template>
  </el-table-column>

  <el-table-column label="" width="120" align="right">
    <template #default="{ row }">
      <RouterLink :to="`/stadium/${row.id}`">
        <el-button size="small">상세보기</el-button>
      </RouterLink>
    </template>
  </el-table-column>
</el-table>
```

`prop="teams"`는 라이브러리 기본 렌더링이고, `<template #default="{ row }">`는
**직접 마크업을 그리는** 방식입니다. 한 표 안에 두 방식이 같이 있어 비교하기 좋습니다.

### ⚠️ 여기서 나오는 구멍

**`<slot :something="value" />` 형태로 자식이 부모에게 데이터를 올려주는 코드가 프로젝트에 없습니다.**
scoped slot을 *소비*만 하고 *정의*한 적은 없습니다.

> **보완 제안**: `DateSelector`가 칩 마크업을 슬롯으로 열어주면 자연스럽습니다.
> ```html
> <slot name="chip" :date="date" :weather="dailyWeather[date]">
>   <!-- 지금 마크업을 fallback으로 -->
> </slot>
> ```
> 그러면 구장 상세와 경기 일정이 각자 다른 칩을 그릴 수 있어 실제 쓸모도 생깁니다.

### Navigation Guard — 접근 차단이 아니라 로딩 UX

```js
// router/index.js:66-85
router.beforeEach((to, from) => {
  // 쿼리스트링만 바뀌는 재진입은 새로 로딩할 게 없으므로 건너뛴다
  if (to.name !== from.name) {
    useUiStore().startRouteLoading()
  }
  // vue-router 5부터 next()는 deprecated. 아무것도 반환하지 않으면 통과
})

router.afterEach(() => useUiStore().endRouteLoading())   // 조건 없이 끔
router.onError(() => useUiStore().resetLoading())
```

**함정 두 개가 여기 있습니다.**

1. **`useUiStore()`를 가드 콜백 *안에서* 부르는 이유** — `main.js`가 router를 import하는 시점은
   `app.use(createPinia())` **이전**이라, 파일 최상단에서 부르면 활성 Pinia가 없어 에러가 납니다
2. **`afterEach`에서 조건을 안 거는 이유** — `beforeEach`와 `afterEach`는 1:1로 짝지어지지 않습니다.
   이동 중 다른 이동이 끼어들면 취소된 쪽은 `afterEach`만 실행되기도 해서,
   조건을 걸면 어긋남이 누적돼 진행 바가 영영 안 꺼집니다

그래서 **라우터는 불리언, API 호출은 카운터**로 자료구조를 다르게 뒀습니다.
API는 `finally`로 짝이 보장되기 때문입니다.

```js
// uiStore.js — 최소 노출 400ms, 안전장치 15초
const MIN_VISIBLE_MS = 400      // 청크가 캐시되면 0ms에 끝나 눈에 안 보임
const SAFETY_TIMEOUT_MS = 15000 // 영원히 떠 있는 것보다 강제로 끄는 게 나음
```

## 관계 ⑫ HomeView ↔ 주소창 — 쿼리 스트링 양방향

**교재는 읽기만 다루지만 여기선 양방향입니다.**

```js
// ① 초기값 복원 — HomeView.vue:38-41
function readSearchFromUrl() {
  const raw = route.query.search
  return typeof raw === 'string' ? raw : ''   // ?search=a&search=b면 배열로 옴
}
const searchQuery = ref(readSearchFromUrl())

// ② 검색어 → 주소창 — :198
watch(searchQuery, (keyword) => {
  if (keyword === readSearchFromUrl()) return        // ← 루프 차단기
  router.replace({                                    // push 아님!
    query: keyword ? { ...route.query, search: keyword }
                   : /* search 키만 제거 */
  })
})

// ③ 주소창 → 검색어 — :211 (뒤로가기 대응)
watch(() => route.query.search, () => {
  const fromUrl = readSearchFromUrl()
  if (fromUrl !== searchQuery.value) searchQuery.value = fromUrl   // ← 루프 차단기
})
```

| 질문 | 답 |
|---|---|
| 왜 `replace`? | `push`면 타이핑 한 글자마다 히스토리가 쌓여 뒤로가기가 망가집니다 |
| 무한 루프는? | ②와 ③이 서로를 부르지만, 값이 같으면 즉시 `return`합니다 |
| 왜 `typeof` 검사? | vue-router는 같은 키가 여러 번 오면 **배열**을 줍니다 |

이 관계 덕분에 **검색 상태가 담긴 URL을 그대로 공유**할 수 있습니다.

**여기서 확인되는 항목**: Query String Routing(양방향), watch(게터 함수 문법), `router.replace`

|---|---|---|
| `Promise.all` | `StadiumDetailView.vue:105` | 3개 다 있어야 화면이 됨 → 하나 실패 시 전체 폴백 |
| `Promise.allSettled` | `HomeView.vue:84` | 현재 날씨는 필수, 예보는 부가 → 예보만 실패해도 살림 |

| `new Set` 중복 제거 | `PlanView.vue:64` | 같은 구장 여러 날짜로 담아도 1회만 호출 |
